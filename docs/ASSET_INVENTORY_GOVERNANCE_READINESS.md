# Governance Readiness Audit (Phase 16)

An audit of Phases 10–15 with authority to repair. Findings were generated from
the repository — every endpoint list, every count and every relationship below
was derived from source or from a live database, not from a previous phase's
document.

**Overall status: READY WITH CONDITIONS.** The architecture is sound and three
defects were found and repaired. Activation is blocked only by a product
decision (P-1/P-7), not by code.

## 3. P0/P1 findings and repairs

### P1-1 — AUTO-3 notified custodians across scopes (Phase 13B gap)

`runMediaOpsAutomations()` selected **every** holder of the
`equipment_custodian` duty and **every** media admin *and sub_admin*, then sent
each one the **asset tag and the name of whoever holds it** for every overdue
loan — with no reference to the asset's scope.

Why it matters: the moment scopes are populated, a custodian of one inventory
is told the tag and holder of an asset in another, which the API itself answers
`404` for. A `sub_admin` is a **Team Lead**, who holds no estate-wide authority
in the scope model, so the leak reached them too.

It survived six phases because every scope audit looked at *routes*, and this
is not a route.

**Repair**
- The scope primitives (`InventoryScope`, `inventoryScopeOf`, `scopeAllows`,
  `inventoryScopeSql`, `pushInventoryScope`, `assetScopeOk`) were **hoisted from
  inside `registerMediaOpsApi()` to module scope**. They were invisible to the
  module-level automation, and the only alternative was a second copy of the
  rule — which is how two answers to one question come to disagree.
- The fan-out now resolves each recipient's scope **once**, before the asset
  loop (no N+1 in a nightly sweep), and filters with the existing
  `scopeAllows()`. **No new rule was introduced.**
- An **unscoped asset allows everyone**, so the legacy estate notifies exactly
  as before. Additive, as Phase 13B established.

### P1-2 — the recipient decision was untestable (same defect's cause)

`escalationFor()` — *which tiers* hear — was exhaustively unit-tested.
*Which people* hear was inline in a function no test can execute:
`runMediaOpsAutomations()` auto-approves leave and writes notifications against
every unrelated fixture in the shared test database, which is why the equipment
suite explicitly declined to call it.

**Repair** — `overdueRecipients()` extracted to `server/equipment-rules.ts`,
pure, following the pattern that file and `mediaops-queries.ts:185` already
use. 8 unit tests. Mutation-tested: removing either scope filter fails a test.

### P1-3 — the legacy estate's WRITE path was unprotected by tests

Found by mutation testing (Section S). Making `scopeAllows()` deny a `NULL`
scope **broke nothing**. Every legacy assertion in the suites was a *read*, and
reads take the `NULL` branch inside `inventoryScopeSql()` in SQL — not
`scopeAllows()`. So `assetScopeOk()`, which **every single-asset write** goes
through, was uncovered on precisely the path that matters most today: all 32
production assets are unscoped, so if that branch ever changed, every custodian
would silently lose the ability to act on the entire estate.

**Repair** — three regression tests: a duty holder with no assignment can edit
an ungoverned asset; a scoped custodian can too (holding a scope must not
*cost* you the legacy estate); an ungoverned asset can still be checked out and
booked. The mutation now fails 3 tests.

## 6. Authorization truth table (Section D) — all verified by test

| Duty | Assignment | Admin | Result |
|---|---|---|---|
| no | no | no | scoped assets **denied** (404); ungoverned estate readable |
| yes | no | no | scoped assets **denied**; ungoverned estate readable **and writable** |
| no | yes | no | in-scope assets **readable**, **not writable** — a scoped *viewer* |
| yes | yes | no | in-scope: **allowed** |
| yes | yes | no | out-of-scope: **denied**, 404 with the endpoint's own message |
| – | – | yes | everything, via `isMoAdmin`; holds **no** assignment row |
| revoked assignment | – | no | denied on the **next request** — never cached |
| revoked duty | assignment stands | no | keeps sight, loses action |

Denials are **404, never 403**, always with the wording that endpoint already
uses for a non-existent id, so an id/tag/QR token is not an existence oracle.

## 7. Section-by-section findings

### E — `mo_user_inventory_scopes`
The Phase 15 surrogate `id` is **necessary and correctly used**. The partial
unique index `(user_id, scope_id) WHERE removed_at IS NULL` is what permits
many historical rows and exactly one live one; with the old composite key,
re-appointment could only be expressed by clearing `removed_at`, destroying the
record. Verified: re-appointment produces two distinct ids, and both concurrent
assignment and concurrent revoke resolve to one row.

### I — asset transfer
Architecturally supportable, **not implemented**, and the preconditions are not
hypothetical: **10 assets are on loan and 25 bookings are live right now**.
History is currently **derived** from the asset's present scope, so a transfer
would retroactively move an asset's entire history between scopes. That is the
same decision as P-8 and must be taken together with P-6.

### J — retired assets (P-10)
**0 retired assets exist**, so no option is foreclosed. The architecture that
best preserves choice is the current one: `scope_id` stays nullable and
retirement stays a separate lifecycle column, so *retain*, *clear* and
*retain-but-inactive* all remain reachable without a migration. **No answer is
implied by the code today.**

### K — pooled inventory (P-9)
**3 assets already carry `pool_quantity`.** The model does not break for them —
they are rows like any other and scope applies unchanged. What breaks is the
*meaning*: one row represents N physical units, so "which scope owns 12 SD
cards" cannot be split without splitting the row. Exactly where it breaks:
`mo_equipment_items.scope_id` is one FK per row, and custody derives from the
latest transaction per row. Nothing needs redesigning **unless** a pool must
span scopes.

### L — borrower readiness
`users` (with `team`), `mo_user_profiles`, `mo_smc_profiles` and the existing
`mountPortalOtp` accountable-non-user pattern can represent student, faculty,
staff and external borrowers **without a second identity system**. The minimum
future seam is a borrower reference on the loan record that resolves to *either*
a `users.id` *or* an accountable non-user — not a new identity table. Inventory
must not become an identity provider.

### M — self-approval / own-inventory borrowing
**Currently undefined and unreachable**, because no request/approval workflow
exists. A custodian *can* today check out an asset from their own scope — that
is ordinary checkout, unchanged since before scopes, and not an approval.
`inventoryScopeOf()` deliberately knows nothing about approval, so both answers
to P-4 and P-5 remain a later policy predicate over `(actor, request, scope)`.
**The seam is preserved.**

### N — database invariants
`NOT NULL` on `scope_id` would fail for **all 32** operational assets today. The
eventual invariant should be **partial**:

```sql
-- NOT YET. After §8 completes.
ALTER TABLE mo_equipment_items ADD CONSTRAINT operational_assets_are_governed
  CHECK (scope_id IS NOT NULL OR retired_at IS NOT NULL OR deleted_at IS NOT NULL) NOT VALID;
```

`NOT VALID` first, so existing rows are not re-checked, then `VALIDATE` once the
estate is clean. Retired and deleted assets are excluded because forcing a scope
onto a retired asset means inventing an owner for something nobody owns.
Blocked on P-9 and P-10.

### P — performance
Measured against a live server:

| | Phase 8 baseline | Now |
|---|---|---|
| `/state` raw | 51,965 B | **51,506 B** |
| `/state` gzip | 6,811 B | **6,759 B** |

67 top-level keys. Largest arrays are all config lookups
(`casting_tags`=25, `automation_rules`=20 …). `equipment_categories` (11 rows)
remains by the Phase 1 decision. **No equipment items, transactions, bookings,
maintenance, scopes or custodian collections are in the boot payload** — a test
asserts it. No N+1 introduced: the custodian list is one query with an `EXISTS`
for the duty, and the AUTO-3 repair resolves scope once per recipient rather
than per asset.

### Q — offline
Every live client path is guarded by `window.__MO_LIVE__`: `eqCatCount`,
`palEqRows` (command palette), `assetPickRows` (pickers), `equip()`,
`trgEquipStatus`, and the kiosk pool all take the server path when live and the
seed only when offline. The `ASSETS` cache is populated **only** from scoped
endpoints, so it can hold nothing the server did not already permit — it is not
a second source of truth. Phase 9/9A behaviour intact.

## 8. Governance activation — what must happen

Enforcement is **real and dormant**: fully implemented, proven by tests,
governing nothing, because no asset carries a scope.

1. **Answer P-1** — which inventories exist and who owns each. *Nothing else
   can start.*
2. **Create the scopes** through the existing admin screen (Admin-only since
   Phase 15).
3. **Answer P-7** — fill the per-asset worksheet. A human decision; §5 proves no
   query can produce it.
4. **Assign assets in batches**, smallest category first. Reversible per asset
   with `UPDATE … SET scope_id = NULL`, no deploy.
5. **Grant the duty and the assignment** to each custodian — neither alone is
   custodianship. **0 people hold the duty today**, so this is a real step.
6. **Verify** the §6 matrix per scope.
7. Only then consider strict mode, the partial constraint, and transfer.

**Steps 1–6 need no code.** The blocker is a decision, not an implementation.
